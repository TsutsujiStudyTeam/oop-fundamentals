# 第12章: インタフェースとは何か

## 核心となる考え
インタフェースは多態性の一種であり**「役割」**である。役割では実体を決められない（「乗り物で来た」では何に乗ったか分からない）。多態性を定義するときは**設計時: クラス → インタフェース**（実体を並べて汎化）、**実装時: インタフェース → クラス**と、手順を180度替える。

## 導入されるフレームワーク
- **多態性（ポリモーフィズム）の定義**: 処理の定義（呼び出し名 + 型 + 引数）が同一でも、処理内部の動きをクラスごとに替えられる機能。Javaでは (1) abstract メソッド (2) Interface (3) override として実現。
- **インタフェース = 役割**
  - 自転車・バイク・自動車・飛行機の役割は「乗り物」（人を乗せて運ぶ）。
  - 「今日は乗り物で来た」→「何に乗ったの?」と疑問が起きる。「自転車で来た」→ 疑問は起きない。
  - **役割では実体を決められない** = 責務でクラスは決まらない（第3章）と同じこと。
- **設計時と実装時の手順逆転**
  | 局面 | 手順 | 方向 |
  |---|---|---|
  | 設計時 | (1) 実体（クラス）を先に並べて比較 → (2) 共通的な処理を抽出 → (3) その処理を再定義（呼び出し名・戻り値・引数を共通化） → (4) インタフェース名を決める | **クラス → インタフェース** |
  | 実装時 | (1) 設計時に決めたインタフェース／抽象メソッドを実装 → (2) それらを実現するクラスを実装 | **インタフェース → クラス** |
  - 乗り物という役割が先にあるのではなく、自転車やバイクを並べてみると乗り物という役割が浮き彫りになる。
  - 実体を並べて共通化・抽象化することを**汎化**という（一般語の「汎用化」と同義）。
- **実体なき多態性は定義できない**: インタフェースや抽象メソッドがクラスより先にできるわけではない。

## 重要概念
- **多態性**: 同一シグネチャで内部動作をクラスごとに替える機能。
- **役割**: インタフェースの本質。実体を決めない。
- **汎化**: 実体を並べて共通部分を抽出すること。
- **abstract メソッド／Interface／override**: Javaの多態性実現手段。

## メンタルモデル
- 「Xで来た」と聞いて「何で?」と聞き返したくなるなら、Xはインタフェース。
- インタフェースを先に切りたくなったら手を止め、「実体クラスを先に洗い出して比較したか?」と問う。問題は順序であって個数ではない。第3章の正解図では「従業員」「ジムの会員」の実現クラスは人間1つだけである。
- 設計は帰納（具体 → 抽象）、実装は演繹（抽象 → 具体）。（派生: 原典の「180度替える」を言い換えたもの）

## アンチパターン
- **実体を並べずにインタフェースから設計する**: 共通化すべき処理が見えておらず、使われないメソッドや合わないシグネチャを生む。
- **インタフェースをクラス（モノ）と混同する**: 第3章の従業員・ジム会員の誤り。

## 具体例（ワーク）
1. （派生: 原典の乗り物の例を設計手順4ステップに当てはめた再構成）設計: 自動車クラスと飛行機クラスを並べる → 共通「人を乗せて運ぶ」を抽出 → シグネチャを統一 → インタフェース名「乗り物」。
2. 実装: インタフェース「乗り物」を先に書き、自動車・飛行機クラスをその実現として実装する。
3. （原典 ch3 の図を本章の設計手順で読み直したもの）受注伝票・発注伝票を並べて「明細の合計金額を返す」「明細の件数を返す」が共通 → インタフェース「明細の一覧を扱う」が浮かぶ。

## 要点
1. インタフェースは役割。役割では実体を決められない。
2. 多態性を定義する際は個別の実体（クラス）を先に並べて共通化する（汎化）。
3. 設計時はクラス → インタフェース、実装時はインタフェース → クラス。視点を180度替える。
4. 多態性はabstractメソッド・Interface・overrideで実現される。

## 関連
- **第1章**: 実現（<|..）の読み方、インタフェース = 役割。
- **第3章**: 責務でクラスは決まらない。役割は Interface にする。
