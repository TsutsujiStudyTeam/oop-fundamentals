# 第1章: 本には書いてないオブジェクト指向（序論）

## 核心となる考え
オブジェクト指向の本質は「隠蔽・継承・多態性」ではなく、**「1箇所直せばみな直る」**を実現するための原理原則である。デザインパターン（定石）を暗記するのではなく、定石を生み出す原理原則（手筋）を理解せよ。

## 導入されるフレームワーク
- **定石と手筋のメタファー**: パターン = 囲碁の定石（有用な常套手段に名前を付けたもの）。このサイトが説く原理原則 = 手筋（定石を産み出す根底の原理）。
  - 使いどころ: パターンを適用するとき。「なぜこのパターンが有効なのか」を原理原則から説明した上で使う。説明できなければ原理原則に立ち返って考え直す。
  - 方法: パターンの奥に隠れた本質（データ構造と処理の一体化、1箇所直せばみな直る）を問う。著者はパターンを否定していない。原理原則を理解すればパターンのみに頼らず正しい設計に辿り着ける、という立場。
- **オブジェクト指向の利点の定義**: 「1箇所直せばみな直る」
  - 初回実装の生産性は手続き型より**低い**。威力を発揮するのは (1) 仕様変更・仕様ミスの修正時、(2) 別システムへの部品流用時。
  - つまり保守性と再利用性が高く、**総合的な生産性**が高い。
- **オブジェクト指向が難しい3つの理由**:
  1. 顧客が要求するのは**処理**であってデータ構造ではないため、データ構造を正しく定義できない。
  2. OO言語は手続き型言語の延長線上にあり、手続き型でも書けてしまう（特にJava）。
  3. RDBとの相性が悪く（インピーダンスミスマッチ）、筋の悪いO/Rマッパーを使うと処理とデータ構造が分離され手続き型に戻る。
  - 対策の第一歩: **処理ではなくデータ構造をまず共通化する**（→ 第8章）。
- **UMLクラス図の3つの関係**（著者が使うのはこの3つのみ）:
  | 関係 | 記法 | 意味 | 例 |
  |---|---|---|---|
  | 関連 | `A "0..*" --> "1" B` | 独立したAとBが互いを参照する | バイク本体とタイヤ |
  | 実現 | `I <\|.. C` | インタフェースIの振る舞いをクラスCが実装する | 乗り物 ← 自動車・飛行機 |
  | 汎化（継承） | `D <\|-- E` | EとFの共通部分を抜き出してDとした。「E is a D」 | 自動車 ← ワゴン車・セダン |

## 重要概念
- **隠蔽・継承・多態性**: OOの特徴ではあるが、初学者の設計理解には「百害有って一利無し」。
- **多重度（カージナリティ）**: 関連に必ず記述する。省略するとそのモデルが扱う業務の目的を理解できない。
- **インタフェース = 役割**: 振る舞いの型（呼び出し名、パラメータ、戻り値）だけを定義し、具体化はクラスに任せる。
- **集約（has a）**: 使わない。ジム・ランボー曰く「集約はプラセボ効果」。関連は双方向参照なので、どちらが持つかを菱形で表す意味がない。
- **インピーダンスミスマッチ**: オブジェクトとRDBの構造的な相性の悪さ。

## メンタルモデル
- パターンを見たら「この定石の手筋は何か」と問え。原理原則に還元してから使う。
- 「この設計は仕様変更時に何箇所直す必要があるか」を常に問え。答えが「1箇所」でなければ、クラスを見逃している。
- クラス図を描くときは著者が使う関連・実現・汎化の3種類で表現する。集約は使わない。

## アンチパターン
- **隠蔽・継承・多態性から教える／学ぶ**: 特徴の説明にはなるが設計の指針にはならず、初学者を手続き型のまま放置する。
- **多重度を省略したクラス図**: 業務の構造（1伝票に明細は1つ以上か、0でもよいか）が伝わらない。
- **集約で持つ／持たれるを表現する**: 関連がある以上どちらも相手を持てるので、菱形の位置は紛らわしさを増すだけ。
- **難しさを理由にOOを回避する**: 著者は「関数型指向と言って手続き型へ回帰するほどOOを回避する傾向」を問題視し、その原因は上記3つの難しさにあるとする。

## 具体例（ワーク）
**関連の多重度を読む**: `受注伝票 "0..*" --> "1" 顧客` は「1人の顧客は0件以上の受注伝票を持ち、1件の受注伝票は必ず1人の顧客を持つ」と読む。この多重度がなければ「顧客不明の受注伝票が存在しうるか」という業務ルールが図から読み取れない。

## 要点
1. OOの利点は「1箇所直せばみな直る」。初回実装の速さではなく、仕様変更と流用で効く。
2. パターン（定石）より原理原則（手筋）を理解せよ。原理原則が分かればパターンに頼らず正しい設計に辿り着ける。
3. OOが難しい根本原因は「顧客の要求は処理であってデータ構造ではない」こと。処理ではなくデータ構造をまず共通化する。
4. クラス図は関連・実現・汎化の3つで描き、多重度は必ず書く。集約は使わない。
5. インタフェースは「役割」と読み替える。
