# 第10章: どのメソッドをどのクラスで実装すべきか

## 核心となる考え
複数クラスの属性を参照するメソッドの実装場所の原則は**2つだけ**。(1) ヘッダと明細のような上下関係があるなら、必要な属性の**最上位クラス**のメソッドにする。(2) 対等・並列なら**第3のクラス**（Mediatorパターン）を作ってそのメソッドにする。

## 導入されるフレームワーク
- **なぜ原則が必要か**: メソッドはパラメータでオブジェクトを渡せるのでAでもBでも実装できてしまう。規則性がないと (1) 第三者が保守しづらい (2) クラス間で不規則にオブジェクトを渡すと変更の影響が思わぬクラスに出て仕様変更に弱い。
- **原則1: 必要な属性の最上位クラスのメソッドとする**
  - 受注総額を返す: 関係クラスは金額、商品単価、商品単価一覧、受注個数、受注明細、受注明細一覧、受注伝票の7つ。実装先は最上位の**受注伝票**。
  - 処理の流れは委譲の連鎖: 受注伝票 → 受注明細一覧.明細総額を返す(受注日付) → [明細ごと] 受注明細.次明細の金額を返す(日付) → 受注個数.個数を返す() / 商品.単価金額を返す(日付) → 商品単価一覧.商品単価を返す(日付) → 金額.乗算値を返す(個数) → 合計用金額.加算する(金額)。
  - **ループは一覧クラスの中に実装する**: 受注明細一覧の実体が配列／List／Map のいずれかは隠蔽されるべき。受注伝票にループを書くと、List→Map の変更で受注伝票も直すことになる。複数の受注明細というデータ構造の最上位は受注明細一覧なので、そこでループする。
  - **受注伝票の「受注総額を返す」を省略しない**: 一覧オブジェクトをアプリに返せば済むように見えるが、一覧だけではどの受注の明細か特定できない。受注伝票が一覧に委譲する形でメソッドを持つ。
- **原則2: 第3のクラスを作る（Mediatorパターン）**
  - 入荷伝票と在庫商品一覧は上下関係がない。「入荷伝票を基に在庫数を増やす」をどこに置くか。
  - 入荷伝票に置く → `在庫数を増やす(在庫商品一覧)`。入荷伝票が在庫商品一覧の仕様を熟知する必要。
  - 在庫商品一覧に置く → `在庫数を増やす(入荷伝票)`。逆に在庫商品一覧が入荷伝票の仕様を熟知。
  - いずれも相手の仕様変更の影響を免れない → **第3のクラス「入荷在庫」**（入荷伝票 "1"—"1" 入荷在庫 "1"—"1" 在庫商品一覧）を作る。GoFの Mediator（仲介者）パターンはこの原則の応用。
  - **注意**: 単なる仲介者として設計すると「仲介する」処理だけのクラスになる。**入荷伝票と在庫商品一覧の両方のデータをひとかたまりとしたクラス**として強く意識して設計する。
  - 強く結びつけたい意図があるなら直接呼び出す密結合でもよい。迷ったら第2原則（疎結合）に従う。
- **複雑な関連の分解**: 複雑な関連も紐解けば最終的に2クラスの関係に分解でき、その2クラスは「上下関係」か「並列関係」のどちらか。だから原則は2つで足りる。

## 重要概念
- **上下関係**: ヘッダと明細のような包含・従属関係。
- **最上位クラス**: 処理に必要な属性を辿ったときの起点となるクラス。
- **Mediator（仲介者）パターン**: 並列関係の2クラスの間に第3のクラスを置く。本書では「両方のデータを持つクラス」として設計する。
- **データ構造の隠蔽**: 一覧の実体（List/Map）を外に見せないこと。ループは一覧の内側。

## メンタルモデル
- 「このメソッドが必要とする属性を持つクラスのうち、一番上はどれか?」→ そこに置く。
- 「2つのクラスに上下はあるか?」→ ない なら第3のクラス。
- 「for文を書こうとしているクラスは、そのコレクションを自分のフィールドに持っているか?」→ 持っていなければ場所が違う。
- 第3のクラスを作るとき「このクラスのデータ構造は何か?」と問い、「両者を合わせたデータ」と答えられるようにする。

## アンチパターン
- **上位クラスで下位コレクションをループする**: コレクション実装の変更が上位に波及。
- **伝票クラスの集計メソッドを省略して一覧オブジェクトを返す**: 文脈（どの伝票か）が失われる。
- **並列クラスの一方に相手を引数で渡すメソッドを置く**: 相手の仕様を熟知する密結合。
- **「仲介するだけ」のMediator**: データを持たない処理クラスになる（派生: 第4章の動詞クラス禁止と同根の誤りと読める）。

## 参照テーブル: 設計クラス図（受注総額）
| クラス | 属性 | メソッド |
|---|---|---|
| 受注伝票 | | + 受注総額を返す(): 金額 |
| 受注明細一覧 | | + 明細総額を返す(日付): 金額 |
| 受注明細 | | + 次明細の金額を返す(日付): 金額 |
| 受注個数 | 個数: 数値, 単位: 文字列 | |
| 商品 | 品名: 文字列 | + 単価金額を返す(日付): 金額 |
| 商品単価一覧 | | + 商品単価を返す(日付): 金額 |
| 商品単価 | | + 日付を返す(): 日付, + 金額を返す(): 金額 |
| 金額 | 金額値: 数値 | + 乗算値を返す(数値): 金額, + 加算する(金額): void |

## 具体例（ワーク）: 入荷在庫（Mediator）のシーケンス
```text
入荷在庫 →[入荷明細の数だけ]→ 入荷伝票.入荷明細を返す()        → 入荷明細一覧.次の入荷明細を返す()
         → 入荷明細.商品を返す(), 入荷明細.個数を返す()
         → 在庫商品一覧.在庫商品を追加する(商品, 個数, 置き場所, 入庫日付)
                → 在庫商品.new(), 商品を設定する(), 個数を設定する(), 置き場所を設定する(), 入庫日を設定する()
```
入荷伝票は在庫の仕様を知らず、在庫商品一覧は伝票の仕様を知らない。両者を知るのは入荷在庫だけ。入荷伝票の明細構造が変わっても在庫商品一覧は無傷。

## 要点
1. 上下関係があれば、必要な属性の最上位に当たるクラスのメソッドにする。
2. 対等・並列なら第3のクラス（Mediator）を作り、両方のデータを持つクラスとして設計する。
3. ループはコレクションを持つ一覧クラスの中に書く。実体（List/Map）を外に漏らさない。
4. 上位クラスの集計メソッドは省略しない（文脈を保つため委譲メソッドを持つ）。
5. 複雑な関連も2クラスの関係に分解でき、上下か並列かのどちらかになる。
6. 密結合にする意図がなければ疎結合（第3のクラス）を選ぶ。

## 関連
- **第4章**: 第3のクラスもデータ構造を持たねばならない（動詞クラス禁止）。
- **第6章**: 一覧クラスがコレクションを内包する。
- **第11章**: 設計クラス図とシーケンス図の往復。
- **GoF Mediator パターン**: 原則2の応用先。
