# 第4章: クラスにするもの

## 核心となる考え
クラスにすべきは要件の中に出てくる**「物」と「結果」**、それにアプリケーションを具現化する**レイアウト／プログラム／メイン**クラス。動詞由来の名前（〜管理、〜制御、Controller、Sender）を持つクラスは処理に着目した誤りであり、作ってはいけない。

## 導入されるフレームワーク
- **役割ではなく状態を考える**
  - 利用者には「何をしてくれるか」が重要だが、設計者は**「それをするためにはどういうデータが必要か?」**を考えて決める。状態はデータ構造によって規定される。
- **クラスの境界線テスト**
  - データ構造 = 「ひとかたまりとして扱いたい情報」。
  - AとBを別クラスにするとは、Aの情報のかたまりとBの情報のかたまりの間に**境界がある**ということ。境界がなければ同じクラスでよい。
  - 例: 売上情報（顧客名・日付・商品・金額）と部門情報（部門名・部門長名・電話番号・住所）の間には人が認識できる境界線がある。
  - 処理に着目すると境界線は見つからない。2つの処理は1クラスにしても2クラスに分けても実装できてしまうから。
- **クラスにしてはいけないものチェック**（「何をクラスにすべきか」より「何をクラスにしてはいけないか」を考える方が近道）
  - 動詞となる名詞が付いたクラス: ファイル送信、データ受信、ログ制御、メッセージ表示、従業員管理。
  - 英語の動詞 + er: Controller, Sender, Receiver。動詞を無理矢理名詞にしただけ。
  - これらは処理の共通化を目的にクラス化されており誤り。多くは**「役割」なので Interface にすべきもの**。
- **物クラスと結果クラス**
  | 種類 | 定義 | 例 | DB上の対応 |
  |---|---|---|---|
  | 物クラス | 実際に存在する物として人間が認識できるもの | 商品、組織、顧客、発注先会社、通貨、日付、氏名、画面上の座標 | マスタデータ |
  | 結果クラス | 人間やシステムが行った結果を記録したもの。商用システムでは「取引」の結果が中心。紙の伝票はすべてこれ。ログも含む | 受注伝票、発注伝票、経理仕訳、アクセスログ、金額 | トランザクションデータ |
- **アプリケーションクラス（3種）**
  | 種類 | 内容 | 持つもの |
  |---|---|---|
  | レイアウトクラス | 画面レイアウト、帳票レイアウト（Excel用、PDF用など出力媒体ごと）。JSP/ASPが該当。「情報の配置図」であり**物クラスの性質** | 画面・帳票上の入力／表示情報 |
  | プログラムクラス | 画面プログラム、帳票プログラム、バッチプログラム。ボタン押下時にどの物・結果クラスを扱うかを知っている | プログラムID、プログラム名称 |
  | メインクラス | アプリ起動の入り口。メイン関数のみ持つ | ログ出力・エラー対応など最低限。プログラムクラスのインスタンスに早く委譲する |
  - メインクラスはアプリ個別に作る場合と汎用的に1つだけ持つ場合がある。
- **オブジェクト図ファースト**: クラスを抽出する前に、具体的なインスタンス（例: 2011年2月20日A社受注01）を並べたオブジェクト図で考える。

## 重要概念
- **境界**: 情報のかたまり同士を分ける、人が認識できる線。クラス分割の根拠。
- **物クラス**: マスタ的な実在物。
- **結果クラス**: 取引・行為の記録。伝票、仕訳、ログ。
- **受注明細**: 「商品／受注個数／商品単価」の組合せとなる結果クラス。商品が受注個数を持つのは誤り（受注のたびに変わるから）。
- **商品単価**: 「ある特定の日の商品の売り値」。商品と日付の2要素で決まる。

## メンタルモデル
- クラス名を見て動詞に戻せるなら（送信→送信する）、それは処理の共通化であり誤り。役割なら Interface に。
- 「紙の伝票に書いてあるもの」はすべて結果クラス。「マスタ台帳に載っているもの」は物クラス。
- 「どんな情報が必要か? どんな状態を持つ必要があるか?」だけをひたすら追求し、あとは組合せ方（関連）を考える。

## アンチパターン
- **動詞クラス（〜管理、〜制御、〜er）**: 処理に着目したクラス化。データ構造の境界がない。
- **物クラスに取引ごとに変わる値を持たせる**: 商品クラスに受注個数を持たせる等。結果クラス（明細）の見逃し。
- **メイン関数に業務処理を書く**: メインは関数にならざるを得ないので、処理は最低限にしてプログラムクラスへ委譲する。

## 具体例（ワーク）: 受注伝票のモデリング
**オブジェクト図**: 受注データ「2011年2月20日A社受注01」= 受注日 2011/2/20、顧客A社、商品X（2011/2/20の単価2800円、受注個数7個）、商品Y（単価680円、受注個数5個）。

**初版クラス図（問題あり）**:
```text
受注伝票 "0..*"→"1" 顧客
受注伝票 "0..*"→"1" 日付(受注日)
受注伝票 "1"→"1..*" 商品
商品 "1"→"1" 受注個数        ← 問題: 受注個数は受注のたびに変わる
商品 "1..*"→"1" 商品単価
日付 "1"→"0..*" 商品単価
商品単価 "1"→"1" 金額
```
**修正版**: 「商品／受注個数／商品単価」の組合せとなる結果クラス **受注明細** を追加。
```text
受注伝票 "1"→"1..*" 受注明細
受注明細 "1"→"1" 受注個数
受注明細 "1"→"1" 商品
商品 "1"→"1..*" 商品単価
日付 "1"→"0..*" 商品単価
商品単価 "1"→"1" 金額
```
商品単価は (1) 受注伝票が持つ日付 と (2) 受注明細が持つ商品 によって特定する。

**アプリケーション構成**: 受注伝票画面レイアウト ─ 受注伝票プログラム ─ メイン、プログラムが受注伝票を扱い、受注伝票以下に上記のモデルが続く。

**プログラムクラスの動き（入荷実績登録画面の登録ボタン）**: (1) 入荷実績登録プログラムクラスの登録メソッドが呼ばれる → (2) 画面レイアウトクラスが持つ入力情報を受け取る → (3) 入荷商品ごとに在庫商品の数量を増加させる → (4) 入荷予定を消し込む。画面の情報を基に複数の結果クラスの状態を変えていく。

## 要点
1. 中心となるクラスは「物」と「結果」。
2. 動詞のクラス（〜管理、Controller等）を作ってはいけない。多くは役割 → Interface。
3. クラスを抽出する前にオブジェクト図でまず考える。
4. 分割の根拠は情報のかたまりの間の「境界」。処理には境界が引けない。
5. アプリ本体はレイアウト／プログラム／メインの3クラスで具現化し、メインは早く委譲する。
6. 設計時は「どんな情報・状態が必要か」だけを追求する。処理は後から付いてくる。

## 関連
- **第3章**: 役割をクラスにしない理由。
- **第5章**: 日付・金額・氏名など、ここで出た物クラスの多くは「小粒クラス」。
- **第6章**: 受注伝票 ⇄ 受注明細の「単位の違い」と一覧クラス。
- **第11章**: オブジェクト図 → 分析クラス図 → 設計クラス図の実践。
