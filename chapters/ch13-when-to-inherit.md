# 第13章: 継承の使いどころ

> **注意**: 原典のこの章は冒頭のみで未完（手形サイトの例の導入で終わっている）。以下は原典に書かれている範囲と、本書の他章の原則から導かれる含意を区別して記す。

## 核心となる考え
継承とは**スーパークラスのデータ構造をサブクラスが引き継ぐ**こと（「拡張」とも呼ぶ）。「クラスとはデータ構造」の原則から、**属性を追加せずメソッドだけを追加する継承はデータ構造が同じなので原則に反し、うまくない設計**である。継承すべきはデータ構造。

## 導入されるフレームワーク（原典記載範囲）
- **継承の2通り**
  1. サブクラスにてメソッドのみを追加する（メソッドのみの拡張） → データ構造が同じ。別クラスにする理由（データ構造の違い）がない。**原則に反する**。
  2. サブクラスにて属性とメソッドを追加する（データ構造の拡張） → 正しい継承。
- **日付クラス → 債権債務日付クラスの例（導入のみ）**
  - 商取引の支払いで使う手形には、振り出しから支払日までの猶予期間 = **手形サイト（支払い猶予期間）、単に「サイト」**がある。
  - 日付クラスにこの属性（サイト）を追加してデータ構造を拡張する継承を考える、というところで原典は終わっている。

## 他章から導かれる含意（原典にはない補足）
- 第5章の数値系クラス群（数値 ← 金額 ← 円貨金額／外貨金額、数値 ← 数量／レート／消費税率）のうち、数量は「単位」、金額は「通貨」、円貨金額は「内/外税区分」、レートは「レート日付」を追加しており、「データ構造の拡張」としての継承の実例になっている（消費税率は原典の図上では属性なし）。
- 第8章: 汎用的なデータ構造を持つクラス（ArrayList等）の継承は、そのデータ構造を熟知していないと副作用があるため、委譲 + private との比較検討が必要。
- 第3章: 役割（従業員・ジム会員）を継承で表すのは誤り。継承はデータ構造の拡張であって役割の付与ではない。

## 重要概念
- **継承（拡張）**: スーパークラスのデータ構造をサブクラスが引き継ぐこと。
- **メソッドのみの拡張**: データ構造が変わらない継承。原則違反。
- **データ構造の拡張**: 属性を追加する継承。正しい使い方。
- **手形サイト**: 手形の振り出しから支払日までの猶予期間。

## メンタルモデル
- 継承を使うとき「サブクラスで追加する属性は何か?」と問う。答えがなければ継承の理由がない（派生: 原典は代替策を明記していない。メソッドをスーパークラスに置くか、役割ならインタフェースを検討）。
- 「is a」が成り立ち、かつ属性が増えるときだけ継承。
- 役割の付与は実現（Interface）、データ構造の拡張は汎化（継承）。

## アンチパターン
- **メソッド追加だけの継承**: データ構造が同じ2クラスが存在することになる。
- **役割を継承で表す**: 第3章の人間／従業員の誤り。
- **汎用コレクションの安易な継承**: 内部構造の理解不足による副作用。

## 具体例（ワーク、原典の導入に基づく再構成）
日付クラス（日付値、翌日／翌月／xx日後を返す）を継承し、債権債務日付クラスに **サイト（猶予期間）** 属性を追加する。支払期日を返すメソッドはサイトを使って計算する。属性が増えているのでデータ構造の拡張であり、正しい継承。もしサイトを属性として追加せず「支払期日を返す(サイト)」メソッドだけを追加したなら、それはメソッドのみの拡張であり、本章の原則（データ構造が同じなら別クラスにする理由がない）に反する。

## 要点
1. 継承はデータ構造を引き継ぎ、拡張すること。
2. 属性を追加しないメソッドだけの継承は原則に反する。
3. 継承を使う前に「追加する属性は何か」を答える。
4. 役割の付与には継承ではなくインタフェース（実現）を使う。
