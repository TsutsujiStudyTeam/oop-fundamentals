# 第3章: 責務はクラスではない

## 核心となる考え
責務（しなければならないこと・出来なければならないこと）は**処理を規定するだけ**で、データ構造を規定できない。だから責務からクラスは決まらない。責務（役割）はクラスではなく**Interface**にせよ。

## 導入されるフレームワーク
- **責務 → Interface、モノ → クラス**
  - 責務 = 利用者側から見た「何をしてくれるか」。設計者はそれだけではクラスを定義できない。
  - Javaの Interface はメソッドを規定するだけで中身は実装者任せ。まさに「責務は決めるがモノは決めない」機能。
  - 著者は Interface を**「役割」**と呼ぶ。本章では責務と役割を同義として扱う。
- **ジュース売りテスト**
  - 責務「ジュース売り」= (1) 注文を聞く (2) 金額を伝える (3) お金をもらう (4) 品物とお釣りを渡す。
  - この責務を請け負えるモノ: 人間、自動販売機（将来はロボットも）。
  - 判定: 責務が決まっても請け負うモノ（データ構造・状態）は複数ありうる → 責務はクラスを決めない。
- **役割の継承 vs 役割の実現（従業員・ジム会員の例）**
  - 誤: `人間 <|-- 従業員`, `人間 <|-- ジムの会員`（継承）。人間の「食事を採る()」が従業員の振る舞いとして継承されるが不要。矛盾が生じる。
  - 理由: モノと呼べるのは**人間だけ**。従業員やジム会員はその人がその時々に負っている**役割**に過ぎない。
  - 正: `<<interface>>従業員 <|.. 人間`, `<<interface>>ジムの会員 <|.. 人間`。役割を負っているときだけ、その役割に必要な振る舞いのみを外部から利用できる。
  - 注: 人事システムでは「人間 = 従業員」が成り立つので従業員をクラスにするのは設計上正しい。ただしそれは**便宜的な省略**であることを忘れない。
- **単一責務の原則（SRP）への反論**
  - SRP: 「クラスを変更する理由が2つあるなら2クラスに分割せよ」（著者の引用元: www.oodesign.com「Single Responsibility Principle」）。
  - 著者: 1つのクラス（モノ）が複数の役割を負うのは普通。役割ごとに Interface を分け、変更はその役割の Interface と実装クラスに対して行えばよい。
  - 例: 受注伝票・発注伝票は「明細の一覧を扱う」（業務的役割: 合計金額・件数を返す）と「RDBを読み書きする」（システム的役割）の2つの Interface を実現する。
  - SRPに従ってRDB読み書きを別クラスに分けると、そのクラスは**データを持たない処理だけのクラス**になり、「データ構造としての伝票クラス」と「RDB処理クラス」に分離されて原理から外れる。
  - 残る課題: 出力媒体（テキスト、ネットワーク…）が増えるたびに伝票クラスにメソッド追加が必要 → 第7章で対応。
- **開発手法の変遷**: 手続き型 → 構造化 → データ中心主義 → オブジェクト指向。OOはデータ中心主義を経て生まれたのに、責務（すること）に着目する設計は過去への回帰。

## 重要概念
- **責務（responsibility）**: しなければならないこと／出来なければならないこと。処理の規定。
- **役割**: 著者による Interface の呼び名。責務と同義。
- **モノ**: データ構造（状態）を持つ実体。クラスになるもの。
- **要件**: 「システムでxxxがしたい」= システムの役割・責務の列挙。処理の記述であってデータ構造は出てこない。
- **「情報を通知する」機能**: どのオブジェクトにも必要な仕組み上の機能であり、特定の役割（責務）ではない。これを責務と呼ぶのは勘違い。

## メンタルモデル
- 「このクラスを請け負えるモノは他にもあるか?」と問え。あるなら、それはクラスではなく役割（Interface）。
- 「乗り物で来た」と聞いて「何で?」と聞き返したくなるなら、「乗り物」は役割である（→ 第12章）。
- 要件（処理）だけを追いかけて設計していると気づいたら、「それをするためにはどういうデータが必要か」に問いを切り替える。

## アンチパターン
- **役割をクラスにする**: 従業員、ジム会員、Controller、Sender…。継承で結ぶと不要な振る舞いが継承され矛盾する。
- **SRPを機械的に適用してデータを持たない処理クラスを切り出す**: データ構造と処理の分離を招く。
- **要件（責務）だけからクラスを導く**: 要件は処理の列挙なのでデータ構造が出てこない。これが誤りの根本。
- **「情報を通知する」を責務に数える**: 仕組み上の機能を役割と混同している。

## 図: 役割をInterfaceにした正しいモデル
```text
<<interface>> 明細の一覧を扱う      <<interface>> RDBを読み書きする
  + 明細の合計金額を返す(): 金額       + RDBから読む(): void
  + 明細の件数を返す(): 数量           + RDBに書く(): void
          ▲ ..実現..                         ▲ ..実現..
   受注伝票 ──────────────────────────── 発注伝票
   (両Interfaceを実現。データ構造=明細一覧等を持つ)
```
- **示していること**: 1クラスが複数の役割を負う。役割ごとに変更箇所が分かれるのは自明であり、分割の必要はない。

## 具体例（ワーク）
**従業員とジム会員**:
1. 業務システムで「従業員クラス」、ジム管理システムで「ジムの会員クラス」が出る。
2. 1人の人の視点で `人間 <|-- 従業員`, `人間 <|-- ジムの会員` と継承で描くと、OOらしく見える。
3. 人間に `食事を採る()`、従業員に `従業員証を提示する()`、ジム会員に `会員証を提示する()` を置くと、従業員が「食事を採る」を継承する。従業員の振る舞いとしては不要 → 矛盾。
4. 原因: モノは人間だけ。従業員・ジム会員は役割。
5. 修正: 従業員・ジム会員を `<<interface>>` にし、人間クラスが両方を実現。人間は `従業員証を提示する()`, `食事を採る()`, `会員証を提示する()` を持つ。役割を負っているときだけ対応するメソッドを外部に見せる。

## 要点
1. 役割（責務）をクラスにしてはいけない。役割は Interface にする。
2. 責務は処理を規定するだけで、データ構造（モノ）を規定しない。
3. 要件だけに着目してもクラスは見つけられない。要件は責務の列挙だから。
4. 1クラスが複数の役割（Interface）を負うのは正常。SRPを根拠に処理だけのクラスを切り出すな。
5. 「責務を全うするにはデータ構造が必要」とは言えるが、責務を考えた結果だけからデータ構造は導けない。

## 関連
- **第2章**: クラスの判別基準はデータ構造（本章はその裏返し）。
- **第4章**: 役割ではなく「それを実行するための状態」を考える具体的手順。
- **第7章**: 出力媒体ごとのメソッド増殖問題と、レイヤ境界での関数の扱い。
- **第12章**: インタフェース = 役割、設計時は「クラス → インタフェース」の順。
