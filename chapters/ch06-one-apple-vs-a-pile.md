# 第6章: リンゴ一個とリンゴ一山は異なるクラス

## 核心となる考え
同じ「リンゴ」でも、一個として扱うか一山として扱うかで属性も処理も異なるので**別クラス**になる。実システムでは**「一件クラス」と「一覧クラス（一山クラス）」を必ず対で設計**し、複数件を扱う要件が出たら必ず一覧クラスを作る。何でもList（配列）に入れる実装は、同じ処理をあちこちに生む。

## 導入されるフレームワーク
- **単位が異なれば別クラス**
  - 一個売りリンゴ: 品種、重さ、売り値、入荷日。
  - 一山売りリンゴ: 品種（同一品種前提）、重さ（総重量）、売り値（総額）、**個数**。さらに「一個あたりの売り値（平均）を返す」メソッドが浮かぶ。
  - 「リンゴ」が分析クラス図に出てきても、一個か一山かを確定させないと正しいクラスとして設計できない。
- **業務上の単位を見逃さない**
  - ここでの単位 = **業務を遂行する人たちがあるものをひとかたまりとして扱う大きさ**（物理単位ではない）。
  - 例: 一伝票、一明細、一会社、一組織、一箱、一取引、一件、一覧。
  - 汎用的な「一個」は「何々一個」と聞き分ける。
- **一件クラスと一覧クラスの対**
  - 要件で「顧客会社クラス」が出たら、「顧客会社一件クラス」と「顧客会社一覧クラス」の2つの可能性がある。ほとんどのシステムで両方必要。
  - 一覧クラスは一件クラスを内部で複数持つ: `顧客会社一覧 "1" → "0..*" 顧客会社一件`。
- **伝票／明細 × 一覧／一件 のマトリクス**
  | モノ | 一覧 | 一件 |
  |---|---|---|
  | 入荷伝票（ヘッダ） | ○ 入荷伝票一覧 | ○ 入荷伝票一件 |
  | 入荷明細 | ○ 入荷明細一覧 | ○ 入荷明細一件 |
  - 伝票一件は明細一覧を**兼ねる**（`入荷伝票一件 "1" → "1..*" 入荷明細一件`）。
  - しかしそれとは別に、**伝票に依存しない入荷明細一覧クラス**も設計する。「全伝票の中から商品Aだけの明細一覧を表示する」要件に対応するため。伝票が明細一覧を兼ねるだけでは「商品Aを持つ複数の入荷伝票」を表現できない。
  - 多重度の違い: 入荷伝票一件 → 入荷明細一件は「1:1以上」（明細0件の伝票は許されない）。入荷明細一覧 → 入荷明細一件は「1:0以上」（検索結果0件はありうる）。
- **RDBなら一レコードクラスと一テーブルクラス**
  - RDBテーブル1つに対して「一レコードクラス」と「一テーブルクラス」を**必ず対で**設計・実装する。
  - 一件クラス ⊇ 一レコードクラス、一覧クラス ⊇ 一テーブルクラス。永続化が必要なものだけが「一レコード／一テーブル」と別名で呼ばれる。
  - 一件クラスに「RDBから一件取得する()」、一覧クラスに「RDBから一覧を取得する(条件)」を実装。伝票一件の取得処理の中で、ひも付く複数の明細を取得する処理も実装する。
- **一山クラスの内部実装**
  - Javaなら List／Map などのコレクションを一山クラスの**内部**で使う。外部にコレクションをさらさない。
  - 商品順に並べたいなら一覧クラス内で TreeMap を使う（入荷商品に重複がない前提）→ ソート処理を別途用意しなくてよい。
  - 業務処理も一覧に実装する: 「数量の一番多い明細を返す()」。

## 重要概念
- **一件クラス**: リンゴ一個に相当。モノ1つ分。
- **一覧クラス／一山クラス**: リンゴ一山に相当。同じものを複数持つ。
- **一レコードクラス／一テーブルクラス**: 一件／一覧クラスのうちRDBに永続化するものの別名。
- **伝票ヘッダ**: ある仕入れ先からのある日の入荷物全体を表す。明細は商品単位。

## メンタルモデル
- 要件に「複数の〜」「〜の一覧」「全〜」と出たら即座に「〜一覧クラス」を立てる。
- 「このデータ構造は一個か一山か?」を分析クラス図の段階で確定させる。
- コレクション（List/Map）はクラスの中に閉じ込める材料であって、クラス間を飛び交う型ではない。

## アンチパターン
- **何でもList（配列）で持ち回す**: 一覧に対する処理（合計、最大、ソート、絞り込み）があちこちに実装される。著者の若手は Grails 開発でこれを見逃し、仕様変更の反映が数十箇所に及んだ（2011年7月）。
- **伝票が明細一覧を兼ねるからと独立した明細一覧クラスを作らない**: 伝票横断の明細検索要件に対応できない。
- **一レコードクラス（Entity）だけ自動生成して一テーブルクラスを作らない**: → 第9章コラム。

## 図: 入荷伝票まわりの完成形
```text
入荷伝票一覧 "1" → "0..*" 入荷伝票一件 "1" → "1..*" 入荷明細一件 "0..*" → "1" 入荷明細一覧
 + RDBから一覧を取得する(条件)   - 仕入れ先会社: 会社     - 商品: 商品          + RDBから一覧を取得する(条件)
                                 - 入荷予定日: 日付       - 予定個数: 数量      + 数量の一番多い明細を返す()
                                 + RDBから一件取得する()  + RDBから一件取得する()
入荷明細一覧 "1" → "1" (List/Map/TreeMapなど) "1" → "0..*" 入荷明細一件
```
- **示していること**: ヘッダ・明細それぞれに一件／一覧がある。明細一覧はヘッダから独立して存在し、コレクションを内包する。

## 具体例（ワーク）
**「商品Aの入荷明細を全伝票横断で表示する」要件**（派生: 原典 ch6 の要件・`RDBから一覧を取得する(条件)`・TreeMap の記述と ch11 の `入荷伝票を返す()` を1シナリオに再構成）
1. 伝票一件が明細を持つだけのモデルだと、商品Aの明細を集めるには全伝票をループして明細を取り出し、呼び出し側で List に詰める処理が各画面に書かれる。
2. 入荷明細一覧クラスに `RDBから一覧を取得する(条件=商品A)` を持たせれば、画面も帳票もこの1クラスを使う。
3. 明細から伝票番号や仕入先を表示したい場合は、入荷明細一件が自分の入荷伝票を返せばよい（第11章の帳票シーケンスを参照）。
4. 「商品順に並べる」要件が後から来ても、一覧クラス内の Map を TreeMap に替えるだけで全利用箇所が変わる。

## 要点
1. 単位が換われば異なるクラスにする。
2. 複数件を扱う場合は一覧クラス（一山クラス）を必ず作る。
3. 一件／一覧は対で設計する。RDBなら一レコード／一テーブルクラスを必ず対で作る。
4. 伝票は明細一覧を兼ねるが、伝票に依存しない明細一覧クラスも別に作る。
5. コレクションとソート・集計処理は一覧クラスの内部に閉じ込める。
