# 第9章: 小粒クラスとユーティリティクラスの関係

## 核心となる考え
「関数禁止」は安易な量産を戒める言葉であり、例外的に許す関数には正しい使い道がある。**異なるクラスの異なる属性を共通的に扱う文字列編集などの関数は、小粒クラスからのみ利用する**。そして、それらは経験のある設計者が設計する。

## 導入されるフレームワーク
- **「小粒クラス → 関数」の2段構え**
  - 氏名クラス `getFullName()`（姓 + スペース + 名）と住所クラス `getAddress()`（郵便番号 + スペース + 居所）は「AとBの間にスペースを1つ入れて返す」という同じ処理。
  - 関数 `StringFunctions.joinWithSpace(a, b)` を作り、両クラスのメソッドから利用する。
  - 仕様変更「氏名のスペースを2つに」→ `joinWithSpace(a, b, spaceSize)` を追加し、`PersonName#getFullName()` だけを修正。社員クラス・取引先クラスなど PersonName を利用するアプリの修正は一切不要。
- **関数利用の運用規則**
  - 「文字列」は業務要件には出てこない**属性の型**であり、文字列編集は極めてシステム的な機能。AとBが文字列でさえあれば業務的特徴に関係なく使えてしまう。
  - 画面アプリや帳票アプリから直接この関数を使うと、スペース1つの変更でもあちこち修正が必要になる。
  - 指標: **この種類の関数は小粒クラスからのみ利用する**。小粒クラスは最小単位のクラスなので、それらに共通する処理があれば関数が必要なケースかもしれないと検討する意義がある。
  - 前提: 経験のある設計者がきちんと設計した上で実装する。さもないとデータ構造を持たない処理が乱造される。

## 重要概念
- **文字列（属性の型）**: システム的な抽象化の結果。業務要件には現れない。
- **joinWithSpace**: 異なる小粒クラスの異なる属性を共通的に扱う関数の典型。
- **リンゴ1個クラス／リンゴ1山クラス**: JPAのEntityは1個クラス。1山クラスを自動生成するツールは見かけない（著者は過去に自作した）。

## メンタルモデル
- 関数の呼び出し元を2層に分ける: 「業務クラス → 小粒クラス → 関数」。業務クラスやアプリが関数を直接呼んでいたら設計の崩れ。
- 「この関数の引数は業務概念か、それとも単なる型か?」単なる型（String, BigDecimal）なら、それを呼ぶ資格があるのは小粒クラスだけ。

## アンチパターン
- **画面・帳票アプリから文字列編集関数を直接呼ぶ**: 仕様変更が全呼び出し箇所に波及。
- **経験の浅い実装者に関数設計を任せる**: データ構造を持たない処理の乱造。
- **Entity（1個クラス）だけ自動生成して1山クラスを作らない**: 1山に実装すべき処理が散らばり、「OOは使いづらい」という印象につながる。

## コード例
```java
public class StringFunctions {
    public static String joinWithSpace(String a, String b) {
        return StringFunctions.joinWithSpace(a, b, 1);
    }
    public static String joinWithSpace(String a, String b, int spaceSize) {
        StringBuffer result = new StringBuffer(a);
        for (int i = 0; i < spaceSize; i++) { result.append(" "); }
        result.append(b);
        return result.toString();
    }
}
/* 小粒クラス PersonName からのみ利用。仕様変更はこの1行だけ */
public String getFullName() { return StringFunctions.joinWithSpace(familyName, givenName, 2); }
/* 小粒クラス Address からのみ利用 */
public String getAddress()  { return StringFunctions.joinWithSpace(zipCode, location); }
```
- **示していること**: 関数は小粒クラスの内側に隠れ、アプリからは `PersonName#getFullName()` しか見えない。

## 具体例（ワーク）
1. 氏名クラスと住所クラスに「スペースで連結」が重複 → 関数 `joinWithSpace` へ。
2. 「氏名はスペース2つ」の変更 → 関数にオーバーロード追加、`PersonName#getFullName()` を1行修正。
3. 社員クラス・取引先クラス・画面・帳票は PersonName 経由なので修正ゼロ。住所は従来通りスペース1つのまま。
4. もし画面が `joinWithSpace(姓, 名)` を直接呼んでいたら、全画面を修正する羽目になった。

## 要点
1. 異なるクラスの異なる属性を共通的に扱う関数・ユーティリティは、小粒クラスからのみ利用する。
2. それらは経験のある設計者が設計する。
3. 「文字列」は型であって業務概念ではない。文字列編集はシステム的機能。
4. 手続き型で書けてしまうこと（Java/C#の関数、Java EEの仕様）がOO実装を阻害している現実を認識する。
5. 1山クラスが常に必要だと気づくのは上級者。設計者が意識して補う。
