# 第2章: クラスとはデータ構造

## 核心となる考え
AクラスとBクラスを別クラスにする理由は「処理が異なる」でも「責務が異なる」でもなく、**「データ構造が異なる」**からである。クラスとはデータ構造（構造体）とそれを扱う処理を一体化したものであり、データ構造を持たないクラスはクラスとして機能しない。

## 導入されるフレームワーク
- **クラス判別の唯一の基準: データ構造**
  - 問い: 「AクラスとBクラスが異なるクラスとして必要な理由は何か?」
  - 選択肢: (1) 処理が異なる (2) 責務が異なる (3) データ構造が異なる → **正解は3**。
  - 使いどころ: クラスを分けるか迷ったとき。処理や責務の違いではなく属性の集まりに違いがあるかを見る。
- **Fields / Methods の同心円モデル**（出典: Oracle Java Tutorials「What Is an Object?」）
  - 中心に Fields（状態 = データ構造）、その外周を Methods（振る舞い）が取り巻く。
  - 含意: 処理はデータ構造の属性を読み書きするために存在する。データ構造がなければ外周のメソッドが取り巻く対象がない。
- **クラスの成り立ち（手続き型からの発展史）**:
  1. 手続き型でも最初に共通するデータ構造（構造体）を決める。
  2. 処理（関数）を作り、処理同士がデータ構造を受け渡してロジックを組む。
  3. 似たような処理が意図せずあちこちに作られる。
  4. 共通関数を作り「共通関数のみ使う」ルールを設けるが、**仕組みとしての強制力がない**ので似た関数が複数生まれる危険は変わらない。
  5. **クラス = データ構造が共通関数を持つことを仕組みとして強要する**。これが危険性を取り除いた。
  - 含意: 関数を共通化するには、まず**受け渡されるパラメータを共通化**する必要がある。複数パラメータをひとかたまりにしたものがデータ構造。手続き型でも処理の共通化に先立ってデータ構造の共通化をしていた。

## 重要概念
- **データ構造**: 属性（プロパティ）の集まり。構造体。
- **処理（メソッド）**: 属性の値を読んだり編集したりするために存在する関数。
- **インスタンス（オブジェクト）**: クラスを基にメモリ上に複数生成される個体。これを複数生成できることがOOの原理。
- **共通関数**: 手続き型での処理共通化手段。ルールによる強制しかなく、重複の危険を排除できない。

## メンタルモデル
- 「このクラスのデータ構造は何か」が答えられないクラスは、クラスではなく関数の置き場である。
- 処理の共通化を考える前に「その処理が受け渡すパラメータは共通化されているか」を問え。共通化されたパラメータのかたまりこそがクラス候補。
- プログラマーは本能的に処理に目が行く。設計者はそれを前提に、曖昧な言葉ではなく**クラス図で**依頼する。

## アンチパターン
- **処理や責務の違いでクラスを分ける**: データ構造の境界がないため、分けても分けなくても実装できてしまい、規則性のない設計になる。
- **データ構造を持たないクラス**: データ構造と処理の一体化という原理に反する。関数の集まりに過ぎない（→ 第7章ユーティリティクラス）。
- **プログラマー任せの製造**: コードだけで考えると手続き型に陥る。クラス図の読み書きを早期に修得させる。

## コード例・図
```text
手続き型:  アプリ ⇄ 関数X ⇄ (データ構造: 氏名・住所) ⇄ 関数Y ⇄ アプリ
           ↑ 関数Xの重複(X', X'')をルールでしか防げない

クラス:    アプリ ⇄ [ クラス { 関数X — (氏名・住所) — 関数Y } ] ⇄ アプリ
           ↑ データ構造が関数を持つことを言語機構で強要
```
- **示していること**: クラスは「共通データ構造 + それに対する共通関数」を一体化して強制する仕組み。

## 具体例（ワーク）
著者が社内の若手に繰り返し教えている言葉は「**クラスとはデータ構造のこと**」。正確には「データ構造と処理を一体化したもの」だが、クラスを見分ける際に最初にやることはデータ構造を考えることなので、あえて単純化して繰り返す。それでも若手は処理に目が行き、すぐ手続き型の考えに戻る。
→ 設計者の対策: (1) 曖昧な言葉による依頼を避け、きちんとしたクラス図を書いて依頼する。(2) プログラマー任せの製造を避ける。(3) コードのみで考える状態から脱却させるため、早いうちからクラス図の読み書きを指導する。

## 要点
1. クラスを規定するのは処理ではなくデータ構造。
2. 別クラスにする唯一の正当な理由は「データ構造が異なる」こと。
3. 処理を共通化するにはまずパラメータ（データ構造）を共通化する。これは手続き型時代から変わらない。
4. クラスは「データ構造が処理を持つ」ことを仕組みとして強要したもの。ルール頼みの共通関数との違いはここ。
5. データ構造を持たないクラスはクラスとして機能しない。
6. プログラマーは処理に目が行く本能があると前提し、設計者はクラス図で設計を伝える。
