# 第8章: Privateメソッド禁止

## 核心となる考え
**privateメソッドを作りたくなったときは、存在すべきクラスを見逃している。** privateメソッドはクラス内の共通関数であり、共通関数を作るにはパラメータの共通化が先に要る。そのパラメータをひとかたまり（データ構造）とするクラスを作り、委譲せよ。隠蔽すべきはフィールドであってメソッドではない。

## 導入されるフレームワーク
- **privateメソッド → 見逃したクラスの検出器**
  - privateメソッドに渡すパラメータの組（例: 姓, 名）= 見逃しているデータ構造。
  - 手順: (1) privateメソッドのパラメータを列挙 → (2) それらを属性とするクラスを定義（氏名クラス: 姓・名） → (3) 処理をそのクラスのpublicメソッドにし、元クラスは委譲する。
- **「1箇所直せば済む」の罠**
  - 顧客会社クラス内に `private getFullName(sei, mei)` を作れば、担当者氏名・代表者氏名のスペース仕様変更は1箇所で済むように見える。
  - しかし仕入れ先会社クラスにも担当者姓・名があれば、同じprivateメソッドがそこにも必要 → 変更箇所は1箇所にならない。
  - **氏名クラス**（姓・名、氏名を返す()）を作れば、顧客会社 "1"—"2" 氏名、仕入れ先会社 "1"—"1" 氏名 となり真に1箇所。
- **パラメータを持たないprivateメソッドはもっとだめ**
  - 「可読性のために長いコードを分割する」は誤り。コードが長くなるのは小物クラスを見逃しまくって手続き的になっているから。
  - 一連の処理なら分割せず処理の流れ通りに1箇所に書いた方が第三者の可読性は高い。
  - 正しいクラスを定義しても長い（属性100個など）なら、それはそれで正しい。意味なく分割しない。
- **同心円モデルからの原理**（Fields を Methods が取り巻く図）
  - メソッドはフィールドを隠蔽するために口を開けている（公開されている）。公開されないメソッドはこの原則に反する。
  - **privateで隠蔽すべきはフィールド（属性）であってメソッドではない。**
- **ユーティリティクラスでもだめな理由（誤用の実例）**
  - `StringUtility.getFullName(a, b)` は「2つの文字列を2個のスペースで連結する」機能に過ぎず、姓名連結のみに使われる保証がない。事務所クラスの `getAtesaki()` が郵便番号と住所の連結に流用しうる。
  - 国際化でミドルネームが追加され「姓 ミドルネーム 名（スペース1つ）」に仕様変更 → 呼び出し元すべてを修正。事務所クラスはミドルネームを持たないので破綻し、別関数が必要になる。
  - 氏名クラスなら、目的が「氏名を構成する属性を保持すること」なので誤用の可能性が低く、`氏名を返す()` の呼び出し側修正は不要。
  - 本質: ユーティリティの目的は**機能の提供**、クラスの目的は**データ構造の保持**。後者は誤用されにくい。
- **例外的にprivateメソッドを許す2ケース**
  1. **再帰処理**: 外部から呼ばれる入口（public、起点をルートに固定）と再帰的に呼ばれる本体（private）の使い分け。例: 二分探索木の走査。
  2. **汎用的なデータ構造を持つクラスを継承せずに委譲で使う場合**: ArrayList などへの特定の扱い（リスト初期化等）を共通化する。継承すれば不要になるが、汎用クラスの継承はデータ構造を熟知していないと副作用があるので、両者のデメリットを比較して選ぶ。

## 重要概念
- **privateメソッド**: クラス内の共通関数。パラメータの共通化 = 見逃したデータ構造。
- **委譲**: 見逃していたクラスを属性として持ち、処理をそのクラスに任せること。
- **小物クラス／小粒クラス**: 見逃すとコードが長くなりprivateメソッドが欲しくなる。
- **隠蔽の対象**: フィールド。メソッドではない。

## メンタルモデル
- `private` と打ちたくなったら手を止め、「このメソッドの引数をフィールドに持つクラスは何か?」と自問する。
- 「同じprivateメソッドが他のクラスにも必要になりうるか?」を問え。なりうるなら、privateは1箇所修正を保証しない。
- 可読性のためにメソッドを切るのではなく、クラスを切る。

## アンチパターン
- **パラメータ付きprivateメソッド**: 見逃したクラスの兆候。
- **パラメータなしprivateメソッド（可読性分割）**: 手続き的な長さをごまかしているだけ。
- **文字列ユーティリティへの逃げ**: 機能提供が目的なので業務的に無関係な属性に流用され、仕様変更で破綻する。
- **汎用コレクションクラスの安易な継承**: データ構造を熟知していないと副作用。委譲 + private の方がましな場合がある。

## コード例
```java
/* 禁止: クラス内共通関数としてのprivateメソッド（顧客会社クラス） */
private String getFullName(String sei, String mei) { return sei + "  " + mei; }
public String getTantoushaFullName() { return getFullName(this.tantoushaSei, this.tantoushaMei); }
public String getDaihyoushaFullName() { return getFullName(this.daihyoushaSei, this.daihyoushaMei); }

/* 正: 氏名クラスに委譲。顧客会社は 担当者氏名: 氏名, 代表者氏名: 氏名 を属性に持つ */
public class Shimei {
    private String sei; private String mei; /* 後にミドルネーム追加も内部で吸収 */
    public String getShimei() { return sei + "  " + mei; }
}

/* 例外1: 再帰処理（入口public、再帰本体private） */
public void traverse() { ascendingTraverse(this.rootNode); }
private void ascendingTraverse(Node current) {
    if (current.getLeftNode() != null) ascendingTraverse(current.getLeftNode());
    /* currentに対する処理 */
    if (current.getRightNode() != null) ascendingTraverse(current.getRightNode());
}
```
- **示していること**: privateの引数（sei, mei）がそのまま氏名クラスの属性になる。

## 具体例（ワーク）: 著者の原体験（2000年頃）
帳票用の自動集計フレームワークを「1箇所直せば皆直る」を心掛けて設計・実装した。本番稼働後の仕様追加で修正しようとしたら、**同じ修正を2箇所にしなければならない**ことが判明。必死に理由を考えた結果「privateメソッドが癌だった」と気づき、新しいクラスを作ってリファクタリングして対応した。→ 原則: OOの出発点は「1箇所直せば皆直る」。難しいことは置いておいても、これを目指して設計・実装すれば核心が見えてくる。

## 要点
1. privateメソッドを作ってはいけない。作りたくなったらクラスを見逃している。
2. privateメソッドのパラメータをひとかたまりとするクラスを作り、委譲する。
3. パラメータなしのprivate（可読性分割）はもっとだめ。長いのはクラス見逃しの結果。
4. 隠蔽すべきはフィールドであってメソッドではない。
5. ユーティリティクラスは機能提供が目的なので誤用され、仕様変更で破綻する。
6. 例外は再帰処理と、汎用データ構造クラスを継承せず委譲で使う場合のみ。
