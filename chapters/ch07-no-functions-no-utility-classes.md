# 第7章: 関数とユーティリティクラスは禁止

## 核心となる考え
**関数 = クラス変数にもインスタンス変数にも一切アクセスしないメソッド**。データ構造に依存しないため「クラスとはデータ構造」の原則に反し、データ構造と処理を分離して保守性を下げる。ユーティリティクラスは関数の単なる集まりなので同様に禁止。例外は**メイン関数、異なるクラスを同一処理で扱う場合、層の境界**の3つだけ。

## 導入されるフレームワーク
- **関数の厳密な定義**
  - クラス変数にもインスタンス変数にも一切アクセスしないメソッド。
  - 例: `getFullName(String surName, String givenName)`、`getSalesTax(BigDecimal amount)`。
  - 帰結: そのオブジェクトのデータ構造に依存しない → データ構造と処理が分離される → 保守性低下。
- **ユーティリティクラス禁止**: 関数の集まりでデータ構造を持たないクラス。弊害の詳細は第8章。
- **例外的に関数を許す3ケース**（例外とはいえ事例は多い）
  1. **メイン関数**: OSが起動パラメータ（データ）をメイン関数（処理）に渡す。プログラム外部から与えられるものと処理は分離せざるを得ない。中身は最低限にし、業務用クラスのオブジェクトに早く委譲する。
  2. **異なるクラスを同一の処理で扱いたい場合**
     - (a) **メディア（媒体）への読み書き**: 受注伝票・発注伝票など数十〜数百のクラスに「RDBに書く」「ネットワークに出力」「テキストファイルに書く」が共通して必要。書き込み先はすべて**別メモリ空間で稼働するシステム**。
       | メディア | メモリ空間 |
       |---|---|
       | RDB | RDBMS |
       | ネットワーク | OS |
       | テキストファイル | OS |
       別メモリ空間にはオブジェクトの状態を渡せない → データ（属性）のみにして渡す → 「データ構造」と「受け渡す処理」が分離 → 受け渡し処理を関数（RDBユーティリティ）として実装する。
     - (b) **Comparator による比較**: `java.util.Comparator#compare(T o1, T o2)` は関数。対象クラスが Comparable を実装していない、または比較対象が異なるクラスの場合に自作 Comparator が必要。
  3. **別メモリ空間のシステムからデータを受け取る場合 = 層（Layer）の境界**
     - プレゼンテーション層 →（HTTP電文）→ アプリケーション層 →（SQL電文）→ RDB層。層と層の間はオブジェクトを渡せないので**電文**でデータ構造を渡す。
     - 電文を受け取るプロセスは各層の処理の起点 = メイン関数と同等。Servlet の `doPost(HttpServletRequest, HttpServletResponse)` がまさにこれ（起動パラメータがHTTP電文に替わっただけ）。
     - 帰結: **層分けをできるだけ行わない方が本来のOOに近づく**（データと処理の分離の発生頻度が減る）。
- **関数を隠すレイヤリング（メディア読み書きの正しい形）**
  - 伝票クラス自身が「属性値をRDBに新規で書き込む()／修正で書き込む()／RDBから削除する()」メソッドを持ち、その中からRDB関数群（最下層はJDBCドライバ）を利用する。
  - プログラムクラス側からは、伝票がデータ構造と処理を一体化した正しいクラスとして見える。
  - O/Rマッパを JDBC の上位に置き「RDBストレージの代理」として表現すると、伝票は **RDBMSオブジェクトに処理を委譲している**形になり、よりOOに近い。

## 重要概念
- **関数**: クラス変数にもインスタンス変数にもアクセスしないメソッド。
- **ユーティリティクラス**: 関数の集まり。データ構造を持たない。
- **メモリ空間**: オブジェクトの状態を共有できる範囲。RDBMS・OSは別メモリ空間。
- **電文**: 層の境界でデータ構造を渡すための、属性のみの形式（HTTP電文、SQL電文）。
- **層（Layer）**: 境界で必ず関数が必要になる構造。

## メンタルモデル
- メソッドを書いたら「インスタンス変数またはクラス変数（static フィールド）を1つでも参照しているか?」を問え。どちらも参照していなければ関数であり、そのパラメータをデータ構造とするクラスを見逃している。
- 「別メモリ空間に渡すか?」で例外判定する。渡すなら関数が必要。ただし関数はクラスのメソッドの**内側に隠す**。
- 層を1つ増やすたびに「データと処理の分離」が1箇所増えると考える。

## アンチパターン
- **安易な関数の量産**: 「関数禁止」はこれを戒める言葉。理解した上で使う関数は問題ない。
- **ユーティリティクラスなしで開発できないと感じる**: 小粒クラスと一山クラスを見逃している証拠。この2種類を設計すれば「関数とユーティリティクラスはいらない」と気づく。
- **プログラムクラスが直接JDBC/O/Rマッパを叩く**: 伝票のデータ構造とRDB処理が分離する。伝票クラスのメソッド内に閉じ込める。
- **不必要な層分け**: 層の境界ごとに関数（電文変換）が増える。

## コード例
```java
/* 関数の例（禁止対象）: どちらもフィールドに一切アクセスしない。原典のタイポ getFUllName / getSalesTaxf は修正して転記 */
public String getFullName(String surName, String givenName) {
    return surName + "  " + givenName;
}
public BigDecimal getSalesTax(BigDecimal amount) {
    BigDecimal tax = new BigDecimal(5);
    return tax.multiply(amount).divide(100, RoundingMode.HALF_UP);
}

/* 例外3: 層の境界 = Servlet の doPost は電文を受け取る関数 */
protected void doPost(HttpServletRequest req, HttpServletResponse resp) { }
```
- **示していること**: 前者は氏名クラス／円貨金額クラスのメソッドにすべきもの。後者はメイン関数と同等であり許される。

## 図: 伝票がRDB処理を内包する形
```text
プログラムクラスA "1"—"1" 受注伝票 ..> O/Rマッパ ..> JDBCドライバ ..> [RDBMS (別メモリ空間)]
                           + 属性値をRDBに新規で書き込む()   + insert(オブジェクト)  + executeUpdate(SQL文)
                           + 属性値をRDBに修正で書き込む()   + update(オブジェクト)
                           + RDBから削除する()               + delete(オブジェクト)
```

## 具体例（ワーク）
**伝票のRDB永続化をどこに書くか**（派生: 原典のクラス図2枚と本文を1シナリオに再構成。手順2の「接続管理」と手順4の「JDBC→O/Rマッパの変更を吸収」は原典に明記されていない推論）
1. 受注伝票・発注伝票それぞれに「RDBに書く」メソッドが要る。中身はJDBCへのSQL発行で、数十クラスで同じ形。
2. 共通部分（SQL発行、接続管理）はデータ構造を持たない → RDBユーティリティ（関数）として切り出す。これは例外2(a)。
3. ただし呼び出すのは**伝票クラス自身のメソッド**から。プログラムクラスには `受注伝票.属性値をRDBに新規で書き込む()` しか見せない。
4. 結果: 伝票を使う側からはデータ構造と処理が一体化して見え、RDB関数の変更（JDBC→O/Rマッパ）は伝票クラス群の内側で吸収できる。

## 要点
1. クラス変数にもインスタンス変数にもアクセスしない処理（関数）を作ってはいけない。
2. 例外は (1) メイン関数 (2) 異なる複数のクラスを同列視したい場合（メディア読み書き、Comparator） (3) 層の間。
3. 例外②のメディア読み書き関数は、データ構造を持つ業務クラスのメソッドの内側に隠して使う。①③は起点なので隠せず、最低限の処理で業務クラスへ即委譲する。
4. 層分けは最小限に。層の境界ごとにデータと処理の分離が発生する。
5. ユーティリティクラスが必要に見えるなら、小粒クラス（第5章）と一山クラス（第6章）を見逃している。
